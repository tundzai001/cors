# UM980 UART diagnostics

## Wiring confirmed by the user

| ESP32 pin | UM980 carrier pin | Direction |
| --- | --- | --- |
| GPIO18 (ESP RX) | T1 / TX1 | UM980 to ESP32 |
| GPIO19 (ESP TX) | R1 / RX1 | ESP32 to UM980 |
| GND | GND | Common ground |

The user reports power applied to the carrier board's marked 5V input. This does not establish the voltage at the UM980 module itself; the module rails and the physical wiring cannot be measured through the ESP32 USB console.

`GNSS_PORT` defaults to 1. It selects receiver output commands (COM1), not ESP32 GPIO numbers. Never automatically reverse GPIO18/GPIO19 or drive other candidate pins.

## Detection and recovery

One driver owns autobaud and physical UART access. It sends only VERSION, VERSIONA, and a checksum-correct UBX-MON-VER query. Detection never sends UNLOG, changes receiver baud, resets the receiver, or saves receiver settings. A valid Unicore command/version response or a checksum-valid UBX-MON-VER response with a 40 + 30*N byte payload is required; generic NMEA or random bytes do not establish the vendor.

The initial scan tries eight documented baud rates: 115200, 460800, 230400, 921600, 38400, 57600, 19200, 9600, with the previously verified baud first. It uses the last verified format, default 8N1. Background retries test one combination at a time, including 8N1, 8N2, 8E1, 8E2, 8O1 and 8O2. A link with no telemetry for 30 seconds is re-probed. Output configuration is blocked until the link is verified. The receive buffer is 4096 bytes.

All receiver logs generated by the ESP32 use the selected receiver COM port. Incoming CORS log commands are remapped to that port. GPIO numbers, detected baud, format and receiver port are included in backend status.

## Serial commands (115200 baud to the ESP32 USB console)

```text
ATG GNSS AUTOBAUD
ATG GNSS AUTOBAUD ALL
ATG GNSS UARTTEST
ATG GNSS SET PORT 1
ATG GNSS SET PORT 2
```

AUTOBAUD scans the eight baud rates. AUTOBAUD ALL scans all 48 documented baud/format combinations. The latter can take about a minute and temporarily owns the GNSS UART; network tasks remain independent. UARTTEST enables hardware loopback internally, transmits eleven bytes, compares the received bytes, and always disables loopback afterward. It does not test GPIO pads, jumper wires, carrier-board traces or the UM980.

SET PORT accepts exactly 1, 2 or 3, saves the selection and restarts the ESP32. To try T2/R2, select port 2, power down both boards, move GPIO18 to T2 and GPIO19 to R2, then power up. Common GND remains required. Restore port 1 for T1/R1. Do not connect two TX outputs together.

## Hardware evidence, 21 October 2026

Firmware was compiled and uploaded to esp_9896E5124B00 on /dev/cu.wchusbserial110. The first direct scan tried all eight baud rates with 8N1 and received zero bytes. A subsequent full scan verified all 48 unique baud/format combinations:

- RX bytes received: 0.
- Valid ASCII responses: 0.
- GPIO18 periodic samples HIGH: 28576; LOW: 0.
- Internal UART1 loopback: PASS, 11/11 bytes.

Periodic GPIO sampling is not an oscilloscope measurement and cannot exclude short pulses between samples. A HIGH level can also occur on a disconnected input. The loopback result establishes internal UART/driver operation, not external wiring. There is still no verified communication with this UM980. Remaining physical checks include continuity to the actual T1/R1 pads, the module supply/reset/boot state, and trying T2/R2. The user reports no direct USB interface or external USB-UART adapter is available.

## Runnable regression check

```sh
c++ -std=c++17 -Wall -Wextra -Werror -I include test/host/probe_checks.cpp -o /tmp/gnss-probe-checks
/tmp/gnss-probe-checks
```

It checks VERSION/VERSIONA, normal and legacy checksums, corrupt data, echo, error replies, generic NMEA, COM3-to-COM1 log routing, and preservation of unrelated configuration commands.

## COM2 and external wire loopback

With GPIO18 connected to T2 and GPIO19 to R2, all 48 baud/format combinations received zero bytes (28604 periodic HIGH samples, zero LOW samples). This leaves receiver-side supply, reset, port state and contacts unresolved.

With both jumper ends disconnected from the receiver and joined together, the ESP received exactly the 31 bytes it transmitted: VERSION, VERSIONA and the UBX poll. This establishes a working external transmit/receive path through GPIO18, GPIO19 and those two wires. It does not establish communication with the UM980.

That experiment exposed a detector bug: a checksum-valid zero-payload MON-VER poll echoed through the wire bridge was incorrectly treated as a u-blox response. Detection now requires the response payload layout (40 + 30*N bytes). Host regression checks reject the poll and accept complete valid responses, including after an echoed poll, while rejecting truncated, corrupt and invalid-length frames.

- Initial external loopback log: /private/tmp/cors-esp32-external-loopback.log (contains the false identity from the old firmware).
- [Official MON-VER response and poll definitions](https://content.u-blox.com/sites/default/files/u-blox-M9-SPG-4.04_InterfaceDescription_UBX-21022436.pdf).

Fixed firmware compiled/uploaded successfully. Repeating the external bridge test at all eight baud rates returned exactly 31 echoed bytes per probe and ended with RX=18 TX=19 COM2 baud=0 chip=UNKNOWN. No receiver was falsely identified. Log: /private/tmp/cors-esp32-external-loopback-fixed.log.

After the user restored GPIO18-to-T2 and GPIO19-to-R2, the corrected firmware repeated all 48 baud/format combinations: zero received bytes throughout, ending COM2 baud=0 chip=UNKNOWN. The prior external wire bridge returned 31/31 bytes at every baud. Receiver-side wiring contacts, carrier identity, supply and reset state remain unverified. Log: /private/tmp/cors-esp32-com2-reconnected-scan.log.
